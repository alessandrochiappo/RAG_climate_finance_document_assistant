# GCF Funding Proposal Assistant

**A retrieval system over 34 Green Climate Fund funding proposals — 3,204 pages of
project documentation — that answers questions in natural language and cites every
claim to a document and page you can click through to verify.**

🔗 **[Live demo](#)** · 34 proposals · 18 countries · $1.50B in approved climate finance

---

## The problem

A GCF funding proposal runs 100–300 pages. An analyst asking *"how do the Nepal projects
differ in their approach to flood risk?"* has no way to answer it except by reading three
documents end to end. Keyword search fails because the proposals say *"dry-season water
deficit"* where the analyst types *"water running out in summer."*

This system answers that class of question in seconds, and — more importantly — makes the
answer checkable. Every factual claim carries a `[FP272, p.15]` label that links straight
to page 15 of the original PDF.

---

## What it does

| | |
|---|---|
| **Ask** | Natural-language questions across the corpus, optionally filtered by country, theme, project size, or minimum funding |
| **Compare** | Run the same question against 2–4 proposals side by side |
| **Portfolio** | Rankings, totals and breakdowns — computed by pandas, never by the model |
| **Refuse** | Out-of-corpus questions are declined in code, before an API call is made |

## Architecture

```
gcf_rag_data.csv
      │
      ▼
 manifest.py ──────────────────────────────┐  structured layer
      │  validates refs, funding, URLs     │  (pandas: exact filtering,
      ▼                                    │   ranking, arithmetic)
 download.py    34 PDFs from source URLs   │
      ▼
 extract.py     pdfplumber → page-indexed JSONL
      │         page numbers attached HERE, by code
      ▼
 chunk.py       21,525 chunks (~800 chars, never crossing a page boundary)
      ▼
 embed.py       all-MiniLM-L6-v2 → 21,525 × 384 dims → Chroma (67 MB)
      ▼
 retrieve.py    question → nearest chunks → deduplicated to 6 full pages
      ▼
 answer.py      6 pages → Gemini → cited answer
      ▼
   app.py       Streamlit
```

### Three decisions that define the system

**1. Two layers, two jobs.**
The manifest (country, theme, funding, ESS category) is structured data; the proposal text
is not. Structured questions — *which project is largest, how much went to Nepal* — are
answered by pandas, exactly. Asking a vector index to rank numbers would be slower and
wrong, so it is never asked to. That split is why the Portfolio tab exists instead of a
plausible-sounding hallucinated ranking.

**2. Retrieve small, send large.**
Chunks (~800 characters) are the unit of *retrieval*; whole pages are the unit of
*reading*. A retrieved chunk is a pointer — the model receives the full page it came from.
The consequence is a hard constraint: **chunks never cross page boundaries**, because a
chunk spanning pages 13–14 would make its own citation a lie.

This paid off three separate times. It let logframe pages be split mechanically on word
boundaries (a chunk only has to be *found*, never read). It made the chunk text redundant
in the vector store, cutting the index from 162 MB to 67 MB. And it meant the
benefit-cost-ratio answer was still correct when its page ranked third rather than first.

**3. Page numbers are attached by code, not generated by the model.**
`extract.py` writes `{"ref": "FP171", "page": 85, "text": ...}` at extraction time. The
model is handed pre-labelled blocks and told to copy the label, and the evaluation checks
every citation against the set of pages actually passed in.

This constrains the failure but does not eliminate it. The model never sees a page it
wasn't given, so it cannot cite *content* from elsewhere — but it can still write a page
*number* it was never handed, and in one measured run it did, three times. The citation
label is the single point in the pipeline where the model must emit a token that is
exactly right rather than merely plausible, and it is the only place the system fabricates.
Measured rate and the parser bug that hid it are in [Evaluation](#evaluation).

## Evaluation

Eight questions with ground truth established by hand — keyword-searching the extracted
text, deliberately independent of the vector index being measured. Metrics follow
[BEIR](https://arxiv.org/abs/2104.08663) for retrieval and
[RAGAS](https://arxiv.org/abs/2309.15217) faithfulness for generation.

| Metric | Result | Stable across runs? | What it measures |
|---|---|---|---|
| Recall@6 | **1.00** | identical, 4/4 | The ground-truth page is in the 6 pages sent to the model |
| MRR | **0.83** | identical, 4/4 | How near the top it ranks |
| Document coverage | **1.00** | identical, 4/4 | Cross-document questions see *all* relevant proposals, not six pages from one |
| Exact figures reproduced | correct | 4/4 | `5.7:1`, `$36.30/tCO2e`, four named lakes — character for character |
| Correct refusal, out of corpus | **1/1** | 4/4 | Decided in code before the API call |
| Invented citations | **rare, non-zero** | **varies** | 1 of 2 correctly-measured runs produced 3 fabricated page numbers |
| Cross-document synthesis | **fails** | 0/4 | The model declines to compare, despite being given every relevant document |

The question set is built to break things, not to flatter: an exact-figure lookup, a
vocabulary mismatch (*"carbon price"* where the document says *"social value of carbon"*),
a false premise, a cross-document comparison, an obliquely worded question, and a question
with no answer in the corpus at all.

**Document coverage is the metric that changed the design.** *"How do the Nepal projects
differ?"* initially returned six pages from one proposal — the model cannot compare what it
never sees. Retrieval now guarantees every matched document a seat before filling the
remaining slots by distance. Coverage went from 0.42 to 1.00.

### What repeated runs revealed

The eval was run four times with no code changes between runs. That was not the original
plan — it happened because a prompt edit appeared to fix one question while breaking
another, and a single run per configuration could not distinguish a real improvement from
chance.

The result splits the system cleanly in two:

**Everything upstream of the language model is deterministic.** Retrieval runs a local
embedding model, so Recall@6, MRR and document coverage were bit-identical across all four
runs. Those numbers are reproducible by anyone who clones the repo.

**Only the generation step varies, and only in one respect.** Answer content was stable;
what moved was citation precision. In one run the model wrote
`[FP170, p.13, 39, 41]` and `[FP170, p.40]` when **only page 13 of FP170 had been
supplied** — three fabricated page numbers in a single answer.

### The evaluation was wrong before it was right

That run initially scored **1** invented citation, not 3. The citation parser was
`\[(FP\d{3}),\s*p\.(\d+)\]` — it required `p.` immediately before a single number, so a
multi-page citation like `[FP170, p.13, 39, 41]` matched nothing at all and the pages
hiding inside it were never checked.

The metric was silently lenient in exactly the direction that flattered the system. An
earlier draft of this README claimed *zero invented citations*, written from one run
scored by a parser that could not see two thirds of them.

The parser now expands multi-page citations before scoring, and `app.py` uses the same
pattern so those citations render as working links rather than dead text. The honest
number replaced the flattering one.

Three times during this build, a citation flagged as wrong turned out to be correct and
the hand-written answer key was the thing at fault. Ground truth written by a human is
itself a source of error, and an evaluation is only ever as good as the person who wrote
the key.

### Refusal is deterministic

Measured distance separation between answerable and unanswerable questions:

| Question | Best distance |
|---|---|
| "What is the benefit-cost ratio of this project?" | 0.306 |
| "Why were early warning systems chosen over flood defences?" | 0.428 |
| **"What is the capital of Brazil?"** | **0.631** |

No overlap, so `MAX_DISTANCE = 0.55` sits in the measured gap and the refusal happens in
`answer.py` before the API call. The model never gets the chance to be helpfully wrong.

## Running it

```bash
git clone https://github.com/alessandrochiappo/RAG_climate_finance_document_assistant.git
cd RAG_climate_finance_document_assistant

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

echo "GEMINI_API_KEY=your_key_here" > .env
streamlit run app.py
```

The vector index (`data/chroma/`) and page text (`data/pages/`) are committed, so the app
runs immediately — no rebuild required.

### Rebuilding the corpus from scratch

```bash
python src/download.py    # 34 PDFs from the manifest's URL column   (~5 min)
python src/extract.py     # PDFs → page-indexed JSONL                (~15 min)
python src/chunk.py       # pages → 21,525 chunks                    (~1 min)
python src/embed.py       # chunks → local vectors                   (~20 min)
python src/eval.py        # run the evaluation suite                 (~3 min)
```

Every stage is idempotent and re-runnable.

## Engineering notes

**pdfplumber over pypdf — decided by evidence, not reputation.** Tested both on ordinary
prose pages with footnotes (a cover page passes in both; a summary form fails in both —
neither discriminates). On FP154 p.46, pypdf's first 1,200 characters were *entirely
footnotes 75–80* — zero body text, because pypdf reads in the order glyphs were drawn.
pdfplumber reads in visual order. A pypdf chunk would weld an unrelated footnote into the
middle of an argument, producing one embedding covering two unrelated topics.

**Running-header stripping.** Every page carries
`GREEN CLIMATE FUND FUNDING PROPOSAL V.2.1 | PAGE 13 OF 126`. Detected by masking digits to
`#` and removing lines repeating on ≥35% of a document's pages — ~23,000 characters from
FP154 alone. Left in, 3,204 near-identical lines drag every chunk's coordinate toward the
same boilerplate, making all chunks more similar to one another. That degrades precisely
what retrieval depends on.

**Ligature repair.** Three proposals use a font whose `ti` ligature has a broken ToUnicode
mapping, extracting as `U+FFFD` — 167 occurrences. Every one was inspected before the fix
was applied: `implementa?on`, `adapta?on`, `communi?es`, `deforesta?on`. The count matters
less than the vocabulary — those are the core searchable terms of climate finance.

**Index size was measured, not estimated.** Full-scale indexes were built with dummy data
before committing to a design:

| Configuration | On disk | Largest file |
|---|---|---|
| 21,525 × 384d, **with** chunk text | 162.0 MB | 124.6 MB ✗ over GitHub's cap |
| 21,525 × 384d, **without** chunk text | 68.1 MB | 36 MB ✓ |

The vectors were never the problem — the chunk text was, at 94 MB of the 162, and it is
never read. Retrieval returns `(ref, page)`; the app loads full page text from
`data/pages/`. Storing the chunk text meant storing the thing it points to, twice. Actual
result after embedding: 67 MB, within 2% of the prediction.

**Local embeddings, forced by measurement.** Gemini's free tier caps batches at 100 texts
and stalls after roughly 700 chunks a day — the corpus would have taken about a month.
`all-MiniLM-L6-v2` runs through ChromaDB's bundled onnxruntime: no new dependency, no
quota, 384 dims, ~20 minutes for the full corpus. The deployment consequence is the
important part: **search runs entirely locally, so the live demo cannot break because a
visitor exhausted a rate limit.** The hosted model is called once per question, only to
write the answer over passages already retrieved.

**A ranking mistake, corrected.** Pages were first ranked by how many retrieved chunks
landed on them. On *"benefit-cost ratio of this project"* that put p.84 (distance 0.348,
4 hits, irrelevant) above p.85 (distance 0.335, 2 hits, **contains the answer**) — the
metric is confounded by page length, since longer pages have more chunks and therefore more
chances to be hit. Reverted to best distance alone. It was overfitting to a single
observation, caught by testing a second case.

## Limitations

These are measured, not hypothetical.

1. **Cross-document synthesis fails on the current model.** Asked *"how do the Nepal
   projects differ in their approach to flood risk?"*, retrieval supplies all three Nepal
   proposals — document coverage 1.00, verified in every run — and the model then declines
   to compare them, saying no passage contains a comparison. Which is literally true: the
   comparison is something it has to *perform*. A prompt rule explicitly licensing
   synthesis did not fix it. Because the eval scores retrieval and generation separately,
   the failure is pinned to the generation stage rather than blamed on search; the next
   thing to try is a stronger model, not a better prompt.
2. **Citations are fabricated occasionally.** Rare, non-zero, and the reason the citation
   parser was rewritten mid-evaluation. See [Evaluation](#evaluation).
3. **Blind to images.** Three pages are Theory of Change and value-chain diagrams — the
   densest causal logic in a funding proposal — and the system reads only the caption.
   Would need a vision model; scoped out deliberately.
4. **Tables degrade.** Budget tables and logframes lose header-to-value association.
   Mitigated by full-page context, not solved.
5. **Weak on exact-value lookups.** Dense retrieval matches *topic*, not literal strings.
   *"Benefit-cost ratio"* surfaced pages *about* economic analysis; the page containing
   `5.7:1` ranked third. Full-page context absorbed it. The standard fix is **hybrid
   retrieval** — vector search merged with BM25 keyword search — and this query is the
   evidence for building it.
6. **88% of the corpus is ESS Category B**, so comparisons on environmental-risk category
   are thin. This reflects the real GCF portfolio rather than a sampling choice.
7. **Cross-page arguments fragment.** An argument spanning pages 13→14 splits.
   Neighbour-page fetching is designed but not built — not until it is measured as a real
   problem rather than an imagined one.
8. **Superlative questions typed into the Ask box are not routed to the manifest.** They
   belong on the Portfolio tab. Automatic routing is the next piece of work.

## What I'd build next, in order

1. **A stronger generation model.** Limitation 1 is the measured case: retrieval already
   supplies everything needed, and the failure is downstream of it.
2. **Hybrid retrieval** (BM25 + dense). Limitation 5 is the measured case for it.
3. **Section tagging.** Every GCF proposal follows the same A–I template, and the thin
   pages in extraction turned out to be section dividers. Tagging each chunk with its
   section would make *"how do these five projects assess risk?"* a filter to section G
   rather than a hopeful search.
4. **Query routing** — classify a question as structured or semantic and send it to pandas
   or to retrieval automatically.
5. **Repeat runs as standard.** Every number in this README came from a single run until it
   didn't. Scoring each question n times and reporting the spread should be the default,
   not the thing you reach for after being burned.
